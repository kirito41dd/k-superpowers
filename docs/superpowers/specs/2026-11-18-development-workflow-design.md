# 5.5.0 研发工作流设计

这版沿用 16 个 skill。SDD 指规格驱动开发（Spec-Driven Development）。约定的行为指导实现和验收，由几个 Agent 完成取决于任务依赖和交接成本。

## 哪些内容跟随代码

假设旧订单原先按下单时的价格结算。如果实现误用了今天的价格，修复后用原约定验收即可。如果产品决定从下个月起按新口径结算，即使代码只改一行，也要更新描述结算行为的文档，写清适用时间、旧订单的处理和验收边界。已有文档放得下就更新原处，重要决定没有合适归属时才新建 spec。配套 spec 默认随获准提交的实现交付。

Plan 给接手任务的 Agent 记录依赖、步骤和验证方式。规划时发现旧订单的处理尚未决定，就把这个选择交给用户，确认后写回 spec，再据此安排任务。只要求计划时，在交接里标出待同步的文档。短期计划可以留在对话里。

从未提交的交付转到 PR 或合并时，要核对实际分支上的提交是否包含已验收的代码和 spec。暂存区里还有待交付文件时，先按提交授权处理。本地合并若共用一个 checkout，更新基线后要切回功能分支进行 rebase 和验证，再把结果合回基线。[Git 交付规则](../../../skills/finishing-a-development-branch/SKILL.md)

## 两个 Agent 怎样共用工作区

假设两个模块都要接入同一接口。接口已定，两个 Agent 分别修改自己的模块，就可以在同一 checkout 并行。如果其中一个任务还会重新生成另一个模块编译时读取的类型，就先确定接口并完成生成，再推进两侧实现。判断依赖要同时看写入、读取和验证所用的输入。

共享 checkout 只有一个暂存区。主 Agent 在派发前记录工作区状态，给每个任务分配可写文件；各任务留下未暂存的改动。写入结束后，主 Agent 核对整批范围、原有用户改动和各任务实际 diff，再运行集成验证。批次检查能发现越界改动，逐项检查才能判断每个任务完成了什么。任务需要独立构建、单独交付或撤回时，才值得承担创建 worktree 和集成结果的成本。[共享工作区验收](../../../skills/subagent-driven-development/SKILL.md)

## 哪些结论需要独立审查

权限判断、持久化语义、跨模块契约等改动一旦出错，影响可能超出当前调用方，因此默认由另一位 reviewer 检查。用户明确要求独立审查时也走这条路径。对于影响局部、能稳定复现的小 bug，主 Agent 可以凭修复前后的行为证据自审交付。如果同类错误容易复发且代价高，再保留一个能拦住回归的自动检查。

审查结论必须对应实际读到的内容。对已提交的改动，打包脚本在入口把两个 Git 引用解析成固定提交 ID。即使分支在打包期间推进，包头、提交列表和 diff 仍来自同一对提交。发现阻断项时，修复后交回原 reviewer 定向复核。[审查输入与复核](../../../skills/requesting-code-review/SKILL.md) · [可重复的 Git 行为检查](../../../tests/git-workflows.sh)
